# Saved terminal monitors

Saved monitors observe public market data and persist in-app alerts independently of the browser. They have no account-key, order, trading, email, webhook, or external-message capability. Existing browser-only monitors remain separate.

Each saved monitor watches either a Kalshi YES last-trade threshold, or one exact Kalshi/Polymarket US pair and direction. Pair values are **gross spreads before fees and slippage**, with settlement equivalence unverified. A trigger is an observation, not an executable arbitrage or profit claim. Market observation time means when a public last-trade quote was successfully checked, not when the underlying trade happened. A last trade may be old or unrepresentative of the current order book. A market must report positive cumulative traded volume; the zero-price placeholder before its first trade is unavailable.

A monitor triggers once, then stays `triggered` until explicitly rearmed. Pause/resume changes its version; rearm also increments its arm version. User changes and worker completion lock the same row. Old claims cannot trigger after a completed pause, delete, rearm, or expired lease. An alert that committed before a pause remains a valid earlier observation. Trigger insertion and monitor state change are one SQL transaction, with a unique monitor/arm key preventing duplicate alerts.

## Deployment requirements

1. Review and separately apply `supabase/migrations/20261015_terminal_monitors.sql` to the application database. This work does not apply that migration. Missing tables/functions return a typed 503, never fake saved state.
2. Configure existing Supabase URL/anonymous/service-role settings in the web server. Authenticated users can select only their own monitor/alert rows. Mutations use session-owned security-definer RPCs; clients cannot write worker fields or alerts. Service-role credentials stay on the web server.
3. Set `TERMINAL_MONITOR_WORKER_SECRET` to a random secret of 32–512 non-whitespace characters. Use a separate value from order review/encryption secrets. The same value is required by the web server and the scheduler.
4. Configure `TERMINAL_MONITOR_BASE_URL` on the scheduler as the web application's HTTPS origin (HTTP is allowed only on localhost for isolated development).
5. Schedule `node scripts/run-terminal-monitors.mjs` once per minute using existing authorized infrastructure, or explicitly run it with `--loop` in a separately managed process. No scheduler, paid service, loop, or deployment is enabled by this change. `TERMINAL_MONITOR_INTERVAL_SECONDS` controls loop delay, default 60, range 60–3600.

The script only calls POST `/api/internal/terminal-monitors` with its bearer token. The route must bypass browser-login redirects and authenticates its own bearer token; it grants no other API capability. Redirects are rejected. The worker claims at most ten due monitors, evaluates at most five concurrently, and does not retry public reads. Pair hydration uses at most four public requests per monitor, so a run has at most forty upstream public requests. Database RPC calls are additional. A global 120-second worker lease prevents overlapping batches; monitor claims expire after 90 seconds. Failed/dead workers do not create completed heartbeats, and abandoned claims can be checked by a later run after expiry. Each completed check schedules the next check at least 60 seconds later. With many users or more than ten due monitors, latency exceeds one minute; oldest due records are selected first.

Health is based on the last actual completed worker run, not merely configured environment variables. It distinguishes not configured, never run, healthy, degraded, and stale (over three minutes). A healthy empty batch does not imply every monitor has fresh data; each monitor exposes its own check status and observation clock. If quote reads fail, lastValue and lastObservedAt retain the last valid observation while lastCheckStatus reports unavailable. Neither stale/future quotes nor closed markets trigger. Pair checks require both fresh live books and positive displayed size; an explicitly old exchange book timestamp is rejected conservatively.

## HTTP contract

All user routes require a Supabase session; mutations require exact same Origin, JSON bodies bounded to 8 KiB, and rate limits. There is a transactionally enforced quota of 25 monitors per user, including paused/triggered ones. The database quota serializes concurrent creates, including direct RPC use.

- GET `/api/terminal/monitors` returns `{monitors, alerts, workerHealth, fetchedAt}`. Alerts are the latest 100, ordered newest first; this is not complete account history. Existing saved records remain readable when the worker is not configured.
- POST `/api/terminal/monitors`: `{target, direction:"above"|"below", threshold, label?}`. Market target is `{kind:"market",ticker}`; opportunity target is `{kind:"opportunity",candidateId,pairDirection}`. Pair directions are `kalshi_yes_polymarket_no` and `polymarket_yes_kalshi_no`; identity is `v1~KALSHI-TICKER~polymarket-us-slug`. Thresholds are dollars (market 0–1; gross spread −1–1), at most four decimal places. Returns `{monitor}` with 201. Creation requires worker configuration, which does not prove the scheduler is running.
- PATCH `/api/terminal/monitors/{id}`: `{action:"pause"|"resume"|"rearm",version}`. Returns `{monitor}`. Pause requires watching; resume requires paused; rearm requires triggered. Target/threshold edits require a new monitor. Version conflicts return 409.
- DELETE `/api/terminal/monitors/{id}?version=N` deletes the owned monitor and its associated alert records, returns 204. Ownership failures are 404; version conflicts are 409.
- POST `/api/internal/terminal-monitors`: worker bearer only, one finite batch. Busy claims return `{status:"busy"}`; completed runs report counts. Missing configuration/storage returns 503.

Pause and delete remain available when worker configuration is missing. Resume/rearm require configuration. There is no automatic resume after a trigger, no settlement verification claim, and no trade placement.

## Verification limits

Offline tests cover validation, exact-direction evaluation, stale/future quote handling, authentication/ownership plumbing, worker flow and failure handling with mocked external boundaries. SQL source defines quota serialization, RLS, claim leases, version fencing and atomic alert insertion; mocks alone do not prove PostgreSQL transaction/locking behavior. Any disposable PostgreSQL results must be reported separately with their exact schema and tested head. Production schema, scheduler operation, public-provider availability and live alerts require separate deployment verification.

Run the offline suite with `node --test src/lib/terminal/persistent-monitor-core.test.mjs src/lib/terminal/persistent-monitor-server.test.mjs`. The optional database regression requires a fresh, empty, dedicated local database named `neutralis_monitor_test_<unique_suffix>` and existing `anon`, `authenticated`, and `service_role` roles. Run `TERMINAL_MONITOR_TEST_DATABASE=neutralis_monitor_test_<unique_suffix> node --test src/lib/terminal/persistent-monitor-sql.test.mjs`. It connects only to the local `/tmp:5432` socket as `postgres`, creates database-local auth stubs, applies this migration, and tests actual RLS, concurrent quota/claim behavior, stale quote retention, pause/delete/rearm fencing, idempotent alerts, and heartbeat leases. It never creates or changes cluster roles and never reads application database credentials. The operator creates and removes the disposable database separately; without the explicit variable this test is skipped.
