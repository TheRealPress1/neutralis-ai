## Current write boundaries

- Live entry: `neutralis/portfolio/manager.py:155–156` calls `save_trade`, then `_upsert_position`. The latter reads the current position, computes totals in Python, then inserts or overwrites it (`:173–213`). There is neither a row lock nor a transactional compare-and-update in that path.
- Storage commits separately: `neutralis/storage/postgres.py:420` trade insert; `:468` position insert; `:499` position update; `:1241` order insert; `:1278` fill insert; `:1322` order status/aggregate update; `:1332` fill-to-trade link. Wrapping unchanged public helpers cannot supply one atomic commit.
- Existing fill/order pipeline: `neutralis/execution/executor.py:112–177` saves order → fill → trade → fill/trade link → position → order aggregates using those helper shapes. Reuse its existing relationships; note that accepted M1 paper execution now targets a process-local `SimulationSink`, not PostgreSQL (`neutralis/execution/mode.py:158–215,306–316`). Do not re-enable persistent paper execution to implement DB isolation.
- `save_order` conflicts return an empty string and skip (`postgres.py:1186–1242`); `save_fill` and `save_trade` have no matching event-aware conflict resolution (`:1244–1279,384–421`). A retried operation with freshly generated local IDs can duplicate economics; a same-key conflict alone cannot prove identical evidence or successful prior application.
- Tenant source is inconsistent: `save_trade` / `save_position` use storage `_user_id` (`postgres.py:417,465`); `save_order` / `save_fill` trust object `user_id` (`:1234,1274`). New application must validate one bound user/account/venue/mode across every row.
- `get_open_position` accepts a mode filter (`postgres.py:573–595`), and recovered `_upsert_position` supplies it. But position updates, order updates, fill linkage and some ID lookups omit user/mode predicates (`:489,597–606,1308,1329,1350–1355`). New atomic entry operations must enforce scope themselves; current migration text does not establish deployed RLS protection.

## Likely changes inside the later checkpoint

1. **One explicit storage transaction per applied entry delta**, on one owned connection: verify bound order/evidence identity and fixed authority → determine unapplied delta → insert/link fill and trade → create/update scoped position → advance applied quantity/consideration and application receipt → commit once. Extract transaction-aware internal operations or a bounded atomic entry method in the existing Postgres storage; do not call the independently committing helpers unchanged or replace the storage system.
2. **Serialize both order progress and position aggregation.** Lock/check the order's durable authority/watermark; protect the existing position against lost updates and handle concurrent creation using the corrected partial uniqueness contract. Row locking alone cannot lock an absent position row. The public `update_position` currently overwrites totals; two workers applying different orders to one position can lose quantity even when fill IDs are unique.
3. **Persist replay identity using existing orders/fills.** Define scoped external order/execution identity and a cumulative authority baseline alongside the original run/request/leg/instrument/action/source binding. Keep alternate evidence distinguishable from applied deltas. Reuse `filled_quantity`/`filled_size_dollars` only after fixing whether they mean observed totals or acknowledged applied totals; those meanings cannot be interchangeable. Do not manufacture economic fill rows for acceptance/unknown evidence to satisfy non-null price/quantity columns.
4. **Return a durable receipt only after commit acknowledgement.** A connection loss during commit remains unknown; reconciliation must look up the same deterministic application identity in existing storage, not rerun submission or blindly mint another Trade/Fill ID. A conflict with changed economics is unresolved, not a successful duplicate. Do not advance in-memory applied baselines before that durable decision.
5. **Preserve continuation semantics.** Current storage context checks live permission on entry, not on pending response delivery (`mode.py:306–313`); `stop_outbound` explicitly leaves recording open (`:243–245`). Do not add arming/kill checks that discard already admitted confirmed outcomes. ARB-FILL-1's application-unknown halt on further writes remains until a separately accepted reconciliation result exists; observations still need retention under their original binding.
6. **Own the connection boundary explicitly.** `postgres.py:41–45` uses a non-autocommit connection after setup; reads and helper calls share it, and `_ensure_connected` can reconnect (`:68–72`). Ensure the atomic method owns a real top-level commit/rollback boundary rather than accidentally nesting inside unrelated work or switching connections mid-application. No venue call belongs inside the DB transaction.

## Migration / compatibility questions before ticket acceptance

- What scoped identity is durable for one user/account/venue/mode/order, and how is each supported venue event or cumulative delta keyed? Keep stable external IDs separate from existing random local IDs and legacy `trades.order_id` semantics; define repeated identical versus contradictory evidence explicitly.
- Replace the open-position index with mode-aware scope, and align SQL `ON CONFLICT` targets with the revised order uniqueness. How are null legacy users, zero-UUID defaults, pre-existing duplicate/ambiguous positions and old writers handled? Migration 023 permits nulls; migration 026 is not reliable provenance. Require a documented legacy/quarantine policy; do not guess founder ownership or backfill history in this task.
- Which minimal added columns/constraints on existing orders/fills preserve bound identity, raw evidence and acknowledged application state without a second ledger? Unknown observations need a representation that does not assert a fill. Define FK/link consistency across user/mode and the trade/fill application cardinality; an FK alone does not prevent duplicate Trade economics.
- Decide exact decimal representation and permitted precision for contracts/consideration before mapping ARB-FILL-1's Decimal deltas into float columns and current rounding (`manager.py:208–213`). Keep unknown fees distinct from the schema's default-zero simulated fees; fee correction/net P&L still belongs to the later fee checkpoint.
- Version a new migration instead of editing/rerunning 010/023/026. Confirm actual migration inventory and PostgreSQL version later under authorized metadata access; local files do not establish deployed schema. Plan index replacement/lock behavior, old/new application compatibility and rollback limits once modes coexist. No production SQL, cleanup, backfill or rollout is implied here.
