Documentation candidate, 2026-09-07 UTC. Base: accepted RH002 `bcb63a265a1175477114cac38f329cfd17ae5e7e`; RH001 remains frozen at `3dd6343cf08b2793da456744e757db67e2abb82e`. ## Finding

**Neutralis as a hosted, server-side HTTP MCP client remains unresolved.** Robinhood explicitly includes other MCP-capable AI platforms, alongside named desktop and hosted products. This is positive provider evidence for general client eligibility, not a closed approved-client list. Its public pages do not specify acceptance of our registration, custom HTTPS redirect, server token custody or unattended refresh. The examined sources contain no explicit prohibition of that design either. General MCP/OAuth standards make it technically plausible; another client's success cannot establish Neutralis acceptance. [P02, P04; M04–M06]

Robinhood requires a desktop device for account onboarding and agent authentication. That describes the owner's interaction, without proving that the MCP client itself must execute on a desktop. Browser-assisted consent followed by server jobs is therefore a proposed architecture, conditional on provider evidence. Discovery is complete for this bounded slice; missing terms are an unresolved contract, not proof that the service is unavailable. [P02; M04]

The proposed application origin is **`https://neutralis.ai`**. Astra supplied a read-only Vercel preflight identifying it and `www.neutralis.ai` as production aliases at source `d524b5a`. This lane did not query Vercel or those origins. No callback path, client ID, registration acceptance or deployed broker route follows from that association. [D1]

## Hosted boundary and exact reuse

The proposed website handles owner interaction; a TypeScript broker boundary owns credentials and provider calls. Later Python research receives a server-owned, minimal serialized research projection, never broker tokens or unrestricted account responses. Source identity, retrieval/cutoff time, field coverage, rights to store/use/share, permitted recipients and provenance must pass the source/rights gate before that projection exists. Root owns feed research and the paper mandate; this slice selects neither a feed nor a strategy. [D1, B2]

There is a concrete bootstrap gap: `ReadPort.catalog` receives identity/version context without a token argument, while `readAccount` already requires an account ID. Its internal read result contains account ID/type, not portfolio or market-data payloads. The later adapter must establish trusted catalog acquisition and owner account selection before that call. It cannot expose provider responses to research by relabelling the existing verification interface. Quotes, financials, order review and all write tools remain outside the two-tool ceiling even when publicly documented. [N1; P03]

RH001's atomic replacement rejects stale refresh completions and retains the old credential until persistence succeeds. It does not provide provider-side refresh serialization across workers. That contract, rotation-reuse behavior, malformed persisted-record validation and maximum token/catalog evidence lifetime remain later work; no unknown provider policy is invented here. [N1; M06]

Conductor remains the development IDE. A future Railway worker could perform jobs after these contracts are reviewed; on-demand local batches can precede it. Supabase could hold small durable owner/consent/audit records and private portable files could hold permitted snapshots. None is provisioned or assumed paid. The website/Railway/Supabase packaging decision does not bypass existing UI003/UI004/Railway holds or authorize production storage. [D1, B2]
