## Closure of the three v1 gaps
1. **One coherent operation, not helpers.** v1 split callback → proof → `buildTokenRequest(proof)` although `AuthorizationProof` carries no code. v2 defines a single server-only `AuthorizationCompletion.complete(...)` that owns the code from validated callback through consume, one exchange, parse and install. The code, verifier and tokens never leave the operation; no exported installer accepts arbitrary tokens.
2. **Stale-completion fence.** The operation binds `proof.expectedRevision` and CASes exactly that revision; it rechecks actor, lifecycle and revision before the exchange and after every `await`; a newer `begin`/`disconnectLocally` or expired owner session denies without installing. Exactly one exchange attempt; an unknown or lost response or persistence acknowledgement is terminal for that code with no retry and no claimed success. No automatic recovery follows. A new owner `begin` works only when the existing domain preconditions allow it. After uncertain persistence, an encrypted credential may already exist: use separately invoked existing metadata/local-disconnect/new-begin lifecycle as appropriate, without clearing or retrying inside completion. No durable operation ledger.
3. **Token identity.** The envelope binds `revision = row.tokenVersion + 1` (matching `ConnectionDomain.identity`, connection.ts:85–88), while the connection row revision increments by one for CAS. Installed state is the existing `awaiting_authorization` with `credential` set and `verification: null`, which `ConnectionDomain.view` already renders as phase `account_verification` (connection.ts:126–127) and `readAccount` consumes unchanged.

## Operation contract (`complete`)
1. `actor(input, time)`; capture immutable validated principal identity, connection ID, callback strings, configuration and policy for the operation (never keep mutable browser-owned values across awaits). Require every returned proof and storage row to match that original user/connection/provider and original proof revision. Revalidate session time after each await and immediately before each effect; never replace the original identity from a mutated input. Parse `params`: any array-valued (duplicate) `code`, `state`, `iss` or `error` → `authorization_mismatch`; any `error` present (with or without `code`) → `authorization_mismatch`, no consume, no exchange; `code` and `state` required single strings within `opaque` bounds.
2. Issuer: `iss` present must equal `ENDPOINTS.issuer` byte-exactly or `authorization_mismatch`. `iss` absent: `issuerPolicy.absent === "reject"` → `authorization_mismatch`; `"allow_unadvertised"` → proceed and record `issuerObserved: false` internally; no issuer value is fabricated. The policy is a trusted construction parameter, never a browser or request parameter. The consume binding passes `issuer: ENDPOINTS.issuer` and `callbackUri: config.callbackUri` from trusted configuration.
3. `transactions.consume(input, connectionId, { state, browserBinding, callbackUri, issuer })` → `proof` (one-time; replay fails inside consume with `authorization_used`/`authorization_mismatch`). Deny with `authorization_mismatch` if `proof.clientId !== config.clientId` or `proof.callbackUri !== config.callbackUri` (config altered after consumption → no request for the altered configuration).
4. Pre-exchange fence: `actor(input, time)` again; `row = store.readOwned(userId, connectionId)`; require `row.revision === proof.expectedRevision`, `row.status === "awaiting_authorization"`, `row.credential === null`; else `stale_version` (revision) or `authorization_mismatch`; no exchange.
5. Request: `url = ENDPOINTS.token`; form exactly `{ grant_type: "authorization_code", code, redirect_uri: config.callbackUri, client_id: config.clientId, code_verifier: proof.verifier, resource: ENDPOINTS.resource }`; no `client_secret`, no Authorization header (advertised auth method `none`). `requestedAt = now(time)` captured immediately before the single `exchange.exchange(...)` call.
6. Result: `failed` → `transport_failed`; `unknown` → `transport_failed` and terminal (code discarded, no retry, no install, no status change); `response` with status ≠ 200 → `invalid_response`, except a valid bounded RFC 6749 §5.2 body with `error: "invalid_grant"` may yield existing `invalid_grant`. Do not infer scope/revocation/account state from generic provider error text. Thrown port errors are redacted `transport_failed`.
7. Parse: body ≤ 65,536 bytes, JSON object; `access_token` non-empty string ≤ 8,192; `token_type` equals `Bearer` case-insensitively; `expires_in` integer with `1 ≤ expires_in ≤ 31,536,000`; optional `refresh_token` string ≤ 8,192; optional `scope` string; unknown members tolerated. `issuedAt = requestedAt`, `expiresAt = requestedAt + expires_in × 1000` (request-time arithmetic). If `now(time) ≥ expiresAt` after processing delay → `token_expired`, no install. Every duration, addition and increment must remain a nonnegative safe integer; use existing time/skew validation and `validateTokens` freshness semantics. These size/lifetime bounds are local admission policy, not observed Robinhood limits. Reject malformed optional fields. Result validated through existing `validateTokens`.
8. Post-exchange fence: `actor(input, time)`; re-read row; require `row.revision === proof.expectedRevision` and unchanged lifecycle as in step 4; else `stale_version`, tokens discarded.
9. Install: `version = row.tokenVersion + 1`; `envelope = vault.seal(JSON.stringify(tokens), { userId, provider: "robinhood", connectionId, keyId, purpose: "tokens", revision: version })`; `next = { ...row, revision: row.revision + 1, tokenVersion: version, credential: { envelope, keyId, expiresAt }, status: "awaiting_authorization", issue: null, verification: null }`; `store.compareAndSwap(userId, connectionId, proof.expectedRevision, next)`. `false` → `stale_version`; throw → `persistence_failed` with unknown persistence outcome, no retry, no success claim. After acknowledged CAS, re-read the owned row and recheck original principal and exact new revision/tokenVersion/lifecycle before producing the existing domain's metadata view; a concurrent replacement, read failure, expired actor or unknown commit cannot become a completion success. No second CAS/exchange or compensating write follows a failed completion. The successful view is phase `account_verification`, `liveEnabled:false`, `canConnect:false`.
10. Redaction: only `IssueCode`s are thrown; no code, state, verifier, token or body fragment appears in errors, receipts or logs. Do not add a production observer/diagnostic callback solely for tests. Tests can count/inspect their owned synthetic port and store calls. If a private internal receipt is used, it contains only issuer-presence and phase/timing facts, never secret material or an invented observed issuer.
