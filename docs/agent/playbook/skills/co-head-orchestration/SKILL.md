# Co-head orchestration

Read the project's current profile, state and applicable instructions. Establish the founder served, repository, dispatch owner, peer session, allowed destinations, budget and stopping point. A saved session ID or shared GitHub identity is not evidence of current ownership.

## Before a dispatch

1. Verify the intended workspace and session against current host metadata and the founder-approved allowlist. Filter discovery by creator and repository. Never message or inspect another team's workspace. Fail closed if ownership or authority cannot be resolved.
2. Reuse an existing authorized lane when appropriate. Give independent product changes separate workspaces and branches; use internal subagents for bounded read-only investigations. Do not let two sessions write one branch.
3. Make the ticket specify outcome, exact reference/artifacts, base commit, fixtures/clock/viewports if relevant, allowed files, exclusions, dependency contracts, proof and stopping point. Require real data capabilities or an honest fallback, not invented fields or fake success.
4. The peer challenges the draft in three lines: ambiguity, room for reinterpretation, and missing artifact-bound acceptance. Resolve material disagreements with evidence or the founder's ruling, without adding process for its own sake.
5. Only the named dispatch owner sends the accepted order. Record its recipient and version in project state. Cross-cutting shared files have one owner; sequence consumers after shared changes.

## During delivery

Follow explicit scope literally and continue autonomously within it. Do not turn a missing unrelated preference into a stop. Escalate missing authority, ownership collisions or product-contract choices that materially change the requested result.

For a literal visual transplant, use the selected reference's composition and shared recipes; do not substitute a new design. Preserve product truth. Never repair a failure merely by changing fixtures or accepting a failing baseline. Fix the defect or obtain approval for an intentional contract change.

Instructions about new copy apply to added/changed lines unless the ticket explicitly commissions a broader sweep. Keep reports short: result, evidence, blocker, next owner.

Builders stop at the authorized boundary, normally PR open. Arrange independent cross-family verification before recommending a merge. Neither peer's confidence substitutes for a passing check or founder approval.

## Handoff and retirement

Persist the exact head, checks, evidence, unresolved findings and next action before replacing a session. Resolve new session IDs from current metadata. Retire the old writer at a PR boundary before the replacement edits. Record capability and budget changes in the project profile; do not silently change reviewer assignment to obtain approval.

A skill describes a workflow. It does not grant additional tool access, permission to launch paid resources, merge, deploy, send mail or change project governance.
